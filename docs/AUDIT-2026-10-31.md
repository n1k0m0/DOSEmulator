# DOSE audit: DOS, Windows 95/98, games and hardware

Audit begun 31 October 2026 against committed `7bb6e474aa38eddd0ffcbab3dfb5b531b0bb956a`.
The resulting local runtime is **C54 / `c54-20261031-audit`**. This review found
five concrete P2 issues and fixes them below. It does not certify every program,
complete historical chips or universal 100% speed. The automation stays paused;
the audit was first qualified locally. Subsequent source publication is
recorded in Git history.

## Findings fixed

| ID / priority | Reproduced problem or source finding | Correction and evidence |
|---|---|---|
| A01 / P2 | A running native backend could label a checkpoint with the hash of a different DLL subsequently placed at its path. | Compare the loaded module MVID with the protected file before hashing that same stream. An actual replacement of an own loaded DLL fails on the previous runtime and is rejected on C54. Invalid replacement PE files also receive a controlled error. |
| A02 / P2 | Native `cpu.json` and `whpx.json` lacked the explicit durable payload flush already used by the nested software snapshot. | Create each new payload exclusively and call `Flush(true)` before publishing the staging directory. This is a source/API durability correction, not a physical power-loss experiment. |
| A03 / P2 | Duplicate/case-aliased native manifest or nested CPU-register keys were accepted; malformed syntax escaped the common invalid-data error path. | Bounded JSON parsing rejects ambiguous object keys recursively and normalizes syntax errors before creating a branch. Six malformed variants and an intact control are exercised. |
| A04 / P2 | Actual WHP register activation could fail after preparation and leave the fresh `.dosebranch` behind. The previous owner already recovered correctly. | Close the prepared PC and its journals before removing only its exact fresh branch. An illegal native CR8 reproduces the failure; the old PC reference, whole 8-MiB RAM, CPU and hardware remain unchanged. |
| A05 / P2 | Native CLI snapshot loading silently ignored some contradictory hardware/media flags, including `--disk1` and `--floppy-a-overlay`. | Reject all 16 conflicting options before loading/creating a branch. Both old acceptance controls reproduce; all 16 new CLI rejection checks pass. |

Implementation: [native snapshot store](../src/DOSEmulator.Whpx/WhpxSnapshotStore.cs),
[activation ownership](../src/DOSEmulator.Whpx/WhpxExecutionFactory.cs),
[CLI](../src/DOSEmulator.Headless/WhpxHeadless.cs),
[permanent native regressions](../tests/DOSEmulator.Whpx.Tests/NativeSnapshotAuditChecks.cs).
The identical final grader fails all three new native audit groups on the old
backend and passes on C54. The identity check follows the existing five-module
MVID policy; it is not attestation against deliberately forged same-MVID files.
The documented [`Flush(true)` API contract](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=net-10.0)
does not establish arbitrary physical disk/controller power-fail behavior.

## Verification performed

The unchanged baseline was freshly tested: **15,471/15,471 common regressions**
and 54 native groups pass. C54 passes **57/57 native groups**, including the three
new permanent groups. Nine common clock cases were repeated against C54; they
are already part of the common total. Builds have zero warnings/errors.

The compiled GUI-owner check covers periodic host-calendar corrections,
retained native RAM, pause/resume, full snapshots, failed loading, both cold
engine switches and the DOS startup media-lease contract. It constructs no
native window and opens no host endpoint. A real old native CLI checkpoint is
rejected with exit 1 before branch creation; a C54 CLI checkpoint loads.

The five software VM modules and common test DLL are byte-identical to C53r1.
Software format 1 therefore keeps its identity. Native format 4 remains bound
to its actual changed WHPX DLL: older native states require their retained
matching runtime. There is no migration. Of 124 product files, ten change;
the old 124 remain byte-identical. All 13 launchers select C54 with the same
eight Windows safety-copy bindings; current user journals were not opened.

Source checks cover **956 code/project files**, including 501 C# files and
5,444 declarations, with no reported issues. State generation remains
48 components / 960 reviewed members / 43 callback operations.

## Actual guests and performance

All runs use named own fixtures and new private working generations. Host
networking and physical audio/video output are disabled. The normal common
native owner performs periodic calendar input and joined scanout. Runs and
timings are serial. Clock following and useful guest work are separate measures.

| C54 actual work | Active clock / host time | Independent useful work |
|---|---:|---|
| Win95 OEM/950, 100 MHz / 64 MiB, strict active-video continuation, 10 s | 99.94% | 200 observed source frames (8..207); 110,251 mono DSP samples |
| Win98 SE, 100 MHz / 128 MiB, cold-started video, 10 s | 99.95% | 201 observed source frames (8..208); 110,250 mono DSP samples |
| Win98 strict active-video continuation, 10.001434 s | 99.91% | 200 observed source frames (8..208); 110,265 mono DSP samples |
| Doom II, 133 MHz / 128 MiB, active SB16 continuation, 20 s | 99.96% | 699 of approximately 700 expected original DEMO1 tics; 441,000 stereo DSP components |

The movie is the complete own 498,496-byte, 320×240 RLE8/PCM source: 360 frames
in 18 seconds, 20 fps and unsigned-8 mono at 11,025 Hz. Actual run durations
are retained; sub-millisecond/millisecond boundary overshoots are not rounded
away when checking sample counts. Published-frame sampling does not prove that
every decoded frame was displayed. Both Windows versions cold-start, reach
natural 18.00-second playback completion, close the player and reach their
regular safe-to-turn-off screen. Both restored copies do so too. All movie
bytes are independently equal in all four sealed FAT journals.

Three genuine native imports (Win95, Win98, Doom with active sound) have exactly
equal initial whole RAM, CPU and hardware digests, with no state exclusions.
They then continue actual guest work. Native future execution follows wall
time; no deterministic whole-future equality is claimed. Later published PCM
is hashed only in RAM, not recorded or played through a host endpoint.

Doom's complete original 4,834-byte DEMO1 is bound to the actual live buffer,
pointer and original reader/writer instructions; 3,591 static HUD pixels are
checked independently against the WAD. The sound configuration is explicitly
`-config sound.cfg`. The accepted sound run returns naturally to DOS and a new
keyboard ECHO succeeds. A separate silent control and preliminary keyboard
mapping/missing-config attempts are excluded from the sound result. One sound
timing attempt hit a sub-tick rounding error in the private test wrapper; it
was discarded, the wrapper corrected, and the active cut imported before the
accepted repeat. No product timing workaround was introduced.

The large-RAM Doom performance fixture uses its already documented own
`HIMEM /TESTMEM:OFF` variant. It is not the original launcher/HIMEM acceptance.
The separate C53r1 original 8-MiB HIMEM full scan, native DOS/Doom return and
486/33-MHz software control retain their qualified unchanged execution paths.
FreeDOS/EMM386 historical cold-start matrices were not re-counted as new tests.

These finite results are close to the 1:1 target, not a new equal-work speedup
factor or a promise for every scene, codec, hardware profile or host. WHPX
executes host-native instructions under the DOSE policy; nominal P54C MHz/TSC
is not a measured historical instruction-retirement rate. The software path
remains the deterministic reference. No additional disk/audio worker, CPU
frequency trick, skipped work or artificial 100% display is introduced.

| Frontends, settings, snapshots, launchers | Compiled owner checks, CLI probes and 13 media-free launcher inspections; no native host-window/input/audio/GL acceptance is inferred. |

The tested Win95 is the supplied OEM/950 family with its narrowly qualified
PDR speed compatibility patches. Current user launcher copies also retain
their installed driver/NDIS corrections. Original Win95 RTM is not accepted by
these tests. Win98 SE requires no such new patch. Manager/remote work, complete
DOSE Tools file transfer and the remaining M4–M8 requirements are not complete.
MMX/newer chipsets/Voodoo and other concept cards must not be inferred from the
current 486/P54C/430FX subset.

Next useful acceptance work is longer combined game/video/storage/network
load, additional real codecs and original drivers, and the explicitly deferred
native frontend/output tests. RTC IRQ8 is a concrete separate hardware feature.
These needs remain visible instead of being converted into a blanket pass.
